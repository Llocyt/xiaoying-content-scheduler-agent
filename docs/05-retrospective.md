# 复盘与下一步

以下是对本次实现和自动化验证的工程复盘，由 Codex 整理。它不代表提交者已经亲自掌握或完成的学习成果。

## 最难的问题

最难的是让可变的模型决策与不可越过的业务边界共存。模型可以选择补查、替代时段或结束，但不能用一句“已保存”替代数据库事实。工具层因此承担审核、授权、幂等、事务和报告生成，模型只决定下一步动作。

另一个难点是确认与重复请求的关系。早期为确认创建新请求 ID，虽然保留了原时间，但不能复用原草稿。改成同一业务请求的授权更新后，必须同时处理摘要稳定性、相同草稿 ID、已确认状态不降级和确认时的竞争占位。

## 实际学到的工程事实

SQLite 连接的事务上下文并不关闭连接，这在 Windows 临时文件清理中暴露为文件被占用。显式关闭连接是运行正确性的一部分。

“函数返回成功”和“事实已提交”需要通过事务与真实持久化回执建立联系。模型输出和最终用户报告需要分开；报告写入失败也不能抹掉已经完成的保存事实。

Mock 可以让故障与并发测试稳定复现，但不能证明真实模型会在复杂观察后做出正确动作。适配器能解析回包，也不等于真实服务验证完成。

## 下一步优先级

1. 提交者配置模型，实际运行并审阅全部 live 场景，优先关注冲突、确认和保存失败路径。
2. 增加多次真实模型重复运行，统计动作合规率、工具错误与任务完成率，保留失败样本。
3. 若扩展业务，再引入多素材聚合、频道维度、真实排期服务和带身份的人工确认；不要先扩大框架复杂度。

当前明确未完成的部分：真实模型决策验证和提交者独立复现记录。UI、部署、多 Agent 和真实发布不在核心交付范围。
